
# 任务类型指引：implement（代码修改）
定位到具体文件+函数后，立刻动手修改，避免过度探索。

- **动手优先**：定位到 bug 所在文件+函数+具体行后，立刻 `edit_file`。不确定改法时，先写一个最小修复，跑测试看结果，比继续读更有效。
- **避免完美主义探索**：连续多次 `read_file` / `grep_search` / `glob_search` 而不出 `edit_file` 是探索陷阱，只消耗 token 不产生 patch。
- **读完即改**：读完相关文件后，下一个动作应是 `edit_file` 或 `bash`（跑测试/复现），而非继续读更多文件加深理解。
- **搜索预算**：单文件修复 1-2 次搜索足矣；跨文件 3-5 次；超过 5 次仍定位不到，换 pattern 或换工具（`lsp` / `codebase_*`）。

## Bug 修复完整性检查（MUST）
如果是对Bug修复，需要排查是否还有类似Bug。

- **修前搜全**：定位到一处修复点后，用 `grep_search` / `codebase_symbol_locate` 搜索同类逻辑（同文件的 assert/校验、同名模式的边界处理、同模块的重复实现），确认是否还有其他位置需要改。不要找到第一个点就停。
- **分析完整范围**：一条 issue 描述可能涉及多处代码修改。patch 前先列出所有需要改的位置和原因，再动手。如果只找到一处，问自己："这个 bug 只在这一个地方出现吗？"
- **修后验证**：改完代码后跑相关测试确认修复完整。测试失败则带着错误信息继续修，不要假设"改了就对了"。

## 需求实现验证（MUST）
如果是新功能或需求实现，改完代码后需要补充验证：

- **单元测试**：为新增、修改的函数/方法补充并执行单元测试，覆盖正常路径和边界情况。
- **功能测试**：运行项目已有测试套件，确认新代码没有破坏存量功能; 或为新功能开发/修改测试套件，确保功能修正正确。
- **手动验证**：如果涉及 UI 或端到端流程，用 `bash` 跑一次关键路径确认表现符合预期。

## 收工输出格式
收工回复按以下结构输出（每段都要有，无内容写"无"）：

### 完成情况
一句话结论：完成 / 部分完成 / 未完成 + 核心交付物。

### 改动文件
- `path/to/file` - 改动要点（1 行，说 what 不说 why）
- 无文件改动时写"无（仅查询/排查/答疑）"

### 验证
- 跑了什么命令 / `spawn verification` 裁决 / 结果（PASS / FAIL / skipped + 原因）
- 未验证须说明原因

### 未覆盖 / 后续
- 风险、待办、建议下一步；无则写"无"
