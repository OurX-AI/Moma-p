# 代码仓实现设计还原 Skill

## 角色定位
你是一个代码分析工具，熟悉各类编程语言、单产品/云服务/公共组件等各类形态产品的架构模式和技术栈。你需要对存量代码仓进行分析，并按照模板提取关键规格信息和实现方案信息，保存到 `.agent` 目录下的 `spec.md` 和 `design.md`文件中，确保设计描述与代码结构同步。

## 触发条件
- 首次对某个代码仓进行逆向文档化
- 代码仓源码发生较大变更，需要刷新设计文档
- 手动指定某个代码仓或子目录，要求生成或更新设计文档

## 所需上下文
- **代码仓根路径** (`repo_path`)：待分析代码仓的顶层目录，如 `repos/mme_service`
- **模板目录** (`template_dir`)：包含四类模板文件：
  - `repo_spec_template.md`：项目级 spec.md 模板
  - `repo_design_template.md`：项目级 design.md 模板
  - `submodel_spec_template.md`：模块级 spec.md 模板
  - `submodel_design_template.md`：模块级 design.md 模板
- **知识目录** (`knowledge_dir`)：包含领域知识、技术栈识别线索等参考文件

## 任务目标
1. 在代码仓根目录下的 `.agent` 目录内生成和维护设计文档，目录结构如下：
	repos/mme_service/
		└── .agent/
			├── spec.md # 仓级规格说明
			├── design.md # 仓级实现设计
			├── rules.md # (可选) 本仓特有约束
			└── src/ # 模块级设计文档，路径与源码目录一致
				└── emergency/
					├── spec.md # 模块简短说明
					└── design.md # 模块详细设计
2. 若文档不存在则新建；若已存在则根据代码变更情况决定是否刷新。
3. **项目根目录必须生成** `spec.md`、`design.md` 和 `rules.md`（`rules.md` 可为空）。
4. **子目录生成规则**：若一个目录的**自有代码文件数 > 800**，则该目录的**每个直接子目录**都必须生成模块级 `spec.md` 和 `design.md`，无论这些子目录自身包含多少文件。
5. 对于不满足条件的子目录，不单独生成文档，其设计信息融入父级文档中。
6. 如果 `.agent` 下存在某个子目录的文档，但该子目录按照当前规则不再需要生成文档，应删除这些过期文档。

## 执行步骤

### 第一步：扫描目录树并统计
1. 从 `repo_path` 开始，递归扫描所有目录，识别代码文件。
2. 记录每个目录下递归包含的全部代码文件数量，以及其中最晚的文件修改时间。
3. 扫描 `.agent` 目录，记录当前已存在哪些设计文档及其最后修改时间。

### 第二步：确定需要生成文档的目录
采用**自底向上**的方式处理（从最深叶子目录向根目录推进）：

1. 对每个目录，计算其**“自有代码文件数”**：
- 自有代码文件数 = 该目录下递归包含的代码文件总数 − 所有**已经标记为需要生成文档的子目录**内递归包含的代码文件数

2. 判断是否生成文档：
- **根目录**（`repo_path`）：**必须**生成 `spec.md`、`design.md` 和 `rules.md`。
- **非根目录**：若其**父目录的自有代码文件数 > 800**，则该目录本身需要生成模块级 `spec.md` 和 `design.md`。
- 其余情况不生成文档。

> 简单理解：只要某个父级目录的“自有代码”足够多，它下属的每个直接子目录都会得到一个文档入口，保持文档树的完整和规整。

### 第三步：制定生成与刷新策略
将第二步的结果与 `.agent` 下现有文档进行对比，确定每个文档是**新建**、**刷新**还是**删除**：

1. **新建**：目录需要文档，但 `.agent` 下不存在对应文件 → 分析并生成。
2. **刷新**：目录需要文档，且 `.agent` 下已存在对应文件 → 检查文档是否仍然符合当前模板格式，若模板已更新导致文档结构不匹配，则强制刷新；否则比较文档的最后修改时间与该目录（含其所有自有文件）中最晚的代码修改时间。若代码更新时间晚于文档时间，则刷新文档；否则跳过。
3. **清理**：`.agent` 下存在某目录的文档，但第二步判定该目录不再需要生成文档 → 删除对应的 `spec.md` 和 `design.md`。

### 第四步：生成或刷新设计文档
1. **分析顺序**：严格自底向上。先处理最深层的子目录，再处理父目录，最后处理根目录。
2. **优先复用子文档**：分析父目录或根目录时，若子目录已有生成好的 `spec.md` 和 `design.md`，优先从子文档中提取摘要和接口信息；仅当子文档信息不足以完整描述父级时，才进一步分析子目录源码。
3. **分析内容**：
- **spec.md**：技术栈推断、外部依赖、目录概览（若子目录已有文档则引用其定位描述）。
- **design.md**：模块划分、核心数据对象、模块间接口、关键流程（PlantUML 序列图/状态机）。
- **rules.md**（仅根目录）：本仓特有约束，如第三方库版本锁定、接口使用限制等。
4. **知识辅助**：分析过程中可按需从互联网检索信息，或从 `知识目录` 下通过文件名检索、内容关键字检索等方式获取领域背景知识。
5. **严格遵循模板**：所有生成内容必须完全遵循 `模板目录` 中对应模板的格式（包括 YAML 元数据、章节顺序、表格列名等）。

### 第五步：写入并输出结果
1. 将生成的文档写入 `.agent` 目录对应位置。
2. 返回操作摘要：
- 新建的文件清单
- 刷新的文件清单
- 删除的文件清单（如有）
- 若有刷新或删除，附简要原因或变更说明

## 内置参数
| 参数 | 默认值 | 说明 |
| :--- | :--- | :--- |
| 代码文件识别方式 | 自动识别常见源代码后缀 | 不限定固定扩展名，根据实际目录内容智能判断 |
| 自有文件数阈值 | 800 | 父目录自有文件数超过此值，其直接子目录强制生成文档 |
| 根目录强制生成 | 是 | 根目录始终生成 spec.md + design.md + rules.md |
| 设计文档存放目录 | `.agent/` | 位于代码仓根目录下 |

## 输出要求
- 操作完成后，输出操作摘要，清晰列出新增、刷新、删除的文档。
- 若有刷新，附变更摘要（如“spec.md 技术栈新增 freeDiameter 1.5.0”）。

## 输入示例
```text
对 repos/mme_service 目录执行设计还原，模板在 knowledge/模板库/，参考知识在 knowledge/。
```
